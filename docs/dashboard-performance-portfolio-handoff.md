이 문서는 이력서·포트폴리오 담당 Codex가 Maple Diary의 대시보드 성능 개선 사례를 정확하고 설득력 있게 작성할 수 있도록 만든 원본 자료다.

## 담당 Codex에게 요청할 작업

아래 사실과 측정값만 사용해 다음 산출물을 작성한다.

1. 이력서용 한 줄 성과 문장 3종
2. 포트폴리오용 문제 해결 사례
3. 면접 30초·1분·3분 답변
4. 기술적 트레이드오프와 후속 개선안

가장 중요한 성과는 번들 크기 자체가 아니라 **사용자가 대시보드에서 정확한 핵심 데이터를 확인하기까지의 시간을 55.1% 단축한 것**이다.

## 발견한 사용자 문제

기존 대시보드는 카드와 레이아웃 자체는 먼저 나타났지만 핵심 수치가 늦게 표시됐다.

- 최초 화면에는 `목표 미설정`, `0회`, `불러오는 중...` 같은 임시 상태가 나타났다.
- React hydration이 끝난 뒤에야 목표·기록·지출·보스 API 요청이 시작됐다.
- API 응답 순서에 따라 일부 데이터만 반영된 잘못된 중간 값이 잠깐 노출됐다.
- 실제 측정 중 목표 진행률이 `0.7%`로 먼저 나타난 뒤 최종값 `54.2%`로 바뀌는 현상도 확인했다.
- 사용자가 대시보드에서 가장 먼저 확인하려는 정보는 화면 틀이 아니라 정확한 목표·수익 수치였다.

## 기존 구조와 병목

```text
브라우저가 초기 HTML 수신
→ React JavaScript 다운로드·실행
→ hydration
→ 클라이언트에서 세션 확인
→ localOwnerId 및 활성 캐릭터 초기화
→ 목표·기록·지출·보스 API 요청
→ 각 API에서 인증 및 Supabase 조회
→ JSON 응답
→ Zustand 상태 업데이트
→ 핵심 수치 재렌더링
```

데이터는 Supabase에 있어 서버에서 초기 요청 시 바로 조회할 수 있었지만, 클라이언트가 실행된 다음 다시 API 서버로 요청하는 추가 왕복이 있었다.

핵심 병목은 다음과 같다.

- hydration 완료 전에는 데이터 요청을 시작하지 못함
- 세션과 로컬 상태 초기화를 기다려야 함
- 브라우저에서 API 서버로 추가 네트워크 왕복 발생
- 여러 API 응답 시점이 달라 부분 데이터 기반 UI가 노출됨
- 빈 상태와 실제 상태 사이에 추가 렌더링 발생

## 적용한 해결 방법

### 1. 대시보드 전용 Server Component 레이아웃 도입

대시보드 하위에 서버 레이아웃을 추가했다. 서버에서 NextAuth 세션을 확인하고 사용자 ID와 활성 캐릭터 ID를 확보한다.

파일:

- `src/app/(main)/dashboard/layout.tsx`

### 2. 서버에서 핵심 데이터 직접 조회

API Route를 브라우저에서 호출하는 대신 서버 렌더링 단계에서 Supabase를 직접 조회한다.

조회 대상:

- 사냥 기록
- 지출
- 목표
- 보스 수익

파일:

- `src/shared/lib/server/dashboard-initial-data.ts`

### 3. 독립적인 데이터 조회 병렬화

네 데이터는 서로의 결과를 필요로 하지 않으므로 `Promise.all`로 동시에 조회한다.

```ts
const [recordsResult, expensesResult, goalsResult, bossResult] =
  await Promise.all([
    loadRecords(),
    loadExpenses(),
    loadGoals(),
    loadBossRevenue(),
  ]);
```

순차 조회라면 전체 대기 시간은 각 조회 시간의 합에 가까워지지만, 병렬 조회는 가장 느린 조회 시간에 가까워진다.

### 4. 초기 HTML에 서버 데이터 주입

서버 조회 결과를 Client Component Provider로 전달한다. 대시보드는 Zustand의 빈 초기 상태보다 서버 스냅샷을 먼저 사용해 실제 수치가 포함된 HTML을 렌더링한다.

파일:

- `src/app/(main)/dashboard/dashboard-initial-data-provider.tsx`
- `src/app/(main)/dashboard/page.tsx`

### 5. 클라이언트 재검증 유지

초기 화면은 서버 데이터로 즉시 구성하지만 hydration 이후에는 기존 Zustand 로딩 로직을 병렬 실행해 최신 데이터를 다시 확인한다.

```text
서버 스냅샷으로 완성된 초기 화면 표시
→ hydration
→ 클라이언트에서 최신 데이터 병렬 재검증
→ 재검증 완료 후 Zustand 데이터로 전환
```

이 구조는 SSR 초기 데이터 주입과 클라이언트 재검증을 결합한 방식이다.

### 6. 실패 시 폴백

서버 초기 데이터 조회가 실패하면 `null`로 처리하고 기존 클라이언트 로딩 경로를 사용한다. 초기 조회 실패가 대시보드 전체 장애로 이어지지 않도록 했다.

## 개선된 흐름

```text
대시보드 요청
→ 서버에서 세션 확인
→ 목표·기록·지출·보스 데이터 병렬 조회
→ 실제 수치가 포함된 HTML 생성

```

## 이력서 추천 문구

### 가장 추천하는 문장

> **대시보드 핵심 데이터 표시 시간 55% 단축(1.54초 → 0.69초)** — hydration 이후 개별 호출되던 목표·기록·지출·보스 데이터를 SSR 단계에서 병렬 조회하고 초기 HTML에 주입해 정확한 핵심 지표가 즉시 표시되도록 개선

### 간결한 문장

> SSR 초기 데이터 주입과 서버 조회 병렬화를 통해 대시보드 핵심 데이터 표시 시간을 1.54초에서 0.69초로 55% 단축

### 구조 개선을 강조한 문장

> 클라이언트 API 4개의 waterfall을 SSR 기반 병렬 데이터 조회로 전환하여 핵심 KPI 표시 시간을 55% 단축하고, 부분 데이터로 인한 잘못된 중간 상태를 제거

주의: 실제 HTTP 요청 자체가 사라진 것은 아니다. 서버의 Supabase 조회는 계속 존재하므로 반드시 **클라이언트 API 의존성 4회 → 0회** 또는 **클라이언트 API waterfall 제거**라고 표현한다.

## 포트폴리오용 서술 예시

### 문제

대시보드 레이아웃은 빠르게 표시됐지만 목표 진행률과 수익 지표는 hydration 이후 여러 API 요청이 완료되어야 나타났다. 사용자는 화면을 보고도 핵심 정보를 바로 확인할 수 없었고, API 응답 순서에 따라 부정확한 중간 값이 노출되기도 했다.

### 분석

목표·기록·지출·보스 데이터는 모두 서버에서 세션을 이용해 Supabase로 직접 조회할 수 있었다. 그런데 기존 구현은 Client Component가 마운트되고 세션 및 로컬 상태가 초기화된 뒤 API Route를 다시 호출했다. 이로 인해 hydration 대기와 추가 네트워크 왕복이 핵심 데이터 표시에 선행했다.

### 해결

대시보드 전용 Server Component 레이아웃을 추가하고, 서버에서 네 데이터를 `Promise.all`로 병렬 조회했다. 조회 결과를 Provider로 Client Component에 전달해 초기 HTML부터 정확한 수치가 포함되도록 구성했다. hydration 이후에는 Zustand 기반 재검증을 수행해 데이터 최신성을 유지했으며, 서버 조회 실패 시 기존 클라이언트 로딩 방식으로 폴백하도록 했다.

### 결과

실제 로그인 데이터와 프로덕션 빌드 환경에서 `navigationStart`부터 최종 목표 진행률이 표시되는 시간을 측정했다. 변경 전·후 각각 5회 콜드 로드의 중앙값을 비교한 결과, 핵심 데이터 표시 시간이 `1,543ms`에서 `692ms`로 줄어 **55.1% 개선**됐다. 또한 일부 데이터만 반영된 진행률이 먼저 나타났다 최종값으로 바뀌던 현상이 사라졌다.

## 면접 답변

### 30초 답변

> 대시보드는 먼저 보였지만 목표 진행률 같은 핵심 수치가 hydration 이후 4개 API 응답을 기다린 뒤 나타나는 문제가 있었습니다. 서버에서 바로 조회할 수 있는 데이터라 판단해 Server Component에서 병렬 조회하고 초기 HTML에 주입했습니다. 실제 로그인 데이터로 최종 목표 진행률 표시 시간을 측정한 결과 중앙값이 1.54초에서 0.69초로 줄어 55% 개선됐고, 부분 데이터 때문에 잘못된 중간 값이 보이던 문제도 제거했습니다.

### 1분 답변

> 기존 대시보드는 Client Component가 먼저 렌더링된 뒤 hydration, 세션 확인, 로컬 ID 초기화를 거쳐 목표·기록·지출·보스 API를 호출했습니다. 따라서 화면 틀은 빨리 보였지만 사용자가 실제로 원하는 수치는 약 1.5초 후에 나타났고, 응답 순서에 따라 진행률이 중간 값에서 최종 값으로 바뀌기도 했습니다. 데이터가 모두 Supabase에 있어 서버에서 바로 조회할 수 있었기 때문에 대시보드 전용 서버 레이아웃에서 세션을 확인하고 네 쿼리를 `Promise.all`로 병렬 실행했습니다. 결과를 초기 HTML에 넣고 hydration 후에는 Zustand로 재검증했습니다. 실제 로그인 세션으로 변경 전후를 5회씩 콜드 로드해 비교한 결과 정확한 목표 진행률 표시 중앙값이 1,543ms에서 692ms로 55.1% 단축됐습니다.

## 예상 면접 질문과 답변 포인트

### 왜 LCP가 아니라 커스텀 지표를 사용했는가?

- LCP는 가장 큰 시각 요소의 표시 시간을 측정한다.
- 이번 문제는 화면의 큰 요소보다 정확한 목표 진행률이 언제 나타나는지가 핵심이었다.
- 따라서 실제 사용자 과업과 직접 연결되는 Dashboard Time to Data를 정의했다.

### SSR이면 무조건 더 빠른가?

- 아니다. 서버가 데이터를 기다리므로 TTFB가 증가할 수 있다.
- 빈 틀만 표시하는 FCP는 기존 CSR이 더 빠를 수도 있다.
- 이 화면은 빈 틀보다 정확한 핵심 데이터의 즉시성이 더 중요하다고 판단했다.
- 병렬 조회로 서버 대기 시간을 줄였다.

### 왜 `Promise.all`을 사용했는가?

- 목표·기록·지출·보스 조회는 서로 독립적이다.
- 순차 실행 시 전체 시간이 각 조회 시간의 합에 가까워진다.
- 병렬 실행 시 전체 시간이 가장 느린 조회 시간에 가까워진다.

### `Promise.all` 중 하나가 실패하면 어떻게 되는가?

- 서버 초기 데이터 로더는 오류를 발생시킨다.
- 대시보드 서버 레이아웃에서 오류를 잡아 초기 데이터를 `null`로 전달한다.
- 클라이언트의 기존 데이터 로딩 경로가 폴백으로 동작한다.

### 데이터가 오래되지 않는가?

- 서버 데이터는 초기 표시용 스냅샷이다.
- hydration 이후 기존 Zustand 로딩 로직이 병렬로 최신 데이터를 재검증한다.
- 재검증 완료 후 스토어 데이터로 전환한다.

### hydration은 무엇인가?

- 서버가 생성한 HTML에 React가 상태와 이벤트 핸들러를 연결해 상호작용 가능한 화면으로 만드는 과정이다.
- 기존에는 hydration 이후에야 데이터 요청이 시작됐다.
- 개선 후에는 hydration 전에도 서버 HTML에 실제 수치가 들어 있다.

## 기술적 트레이드오프

- 사용자별 데이터를 서버에서 조회하므로 `/dashboard`가 정적 페이지에서 동적 서버 렌더링 페이지로 변경됐다.
- DB 조회만큼 TTFB가 증가할 수 있다.
- 서버가 사용자별 조회 부하를 부담한다.
- 초기 서버 데이터와 클라이언트 재검증 데이터 사이의 전환 정책이 필요하다.
- 대신 정확한 핵심 데이터가 첫 화면부터 표시되고 클라이언트 waterfall과 중간 상태 오류가 제거됐다.

## 후속 개선 후보

- 서버 데이터 조회 결과 중 대시보드에 필요한 필드만 선택해 RSC payload 축소
- 전체 기록 대신 대시보드 기간과 최근 개수에 필요한 행만 서버에서 조회
- Supabase 인덱스와 쿼리 실행 계획 점검
- 각 서버 쿼리 latency를 계측해 가장 느린 조회 최적화
- Suspense와 streaming을 사용해 중요도가 낮은 섹션을 점진적으로 전달
- 클라이언트 재검증 중복 요청을 TTL 또는 React Query hydration으로 제어
- 운영 환경의 Real User Monitoring으로 실제 Time to Data 분포 수집

## 함께 진행된 별도 성능 개선

이 항목들은 핵심 데이터 55% 단축 사례와 구분해서 보조 성과로 사용할 수 있다.

- 분석 페이지의 보스 수익 API 요청 `3회 → 1회`
- 대시보드·목표 페이지의 보스 수익 API 요청 `2회 → 1회`
- 기록·지출 전역 모달을 `next/dynamic`으로 분리해 열 때만 로드
- 단순 막대그래프에서 Chart.js를 제거하고 CSS 기반 그래프로 교체
- `chart.js`, `react-chartjs-2` 및 하위 의존성 제거
- 보스·채집·목표 이미지에 `next/image` 적용
- 번들 분석에서 Chart.js 모듈 제거 및 모달의 dynamic entry 분리 확인

별도 Lighthouse 콜드 로드 측정에서는 다음 변화가 관측됐지만, 핵심 사례의 대표 수치로는 사용하지 않는 편이 좋다.

- Lighthouse Performance: 91 → 95
- LCP: 3.56초 → 3.01초
- 초기 JavaScript 전송량: 약 469KB → 407KB
- 메인 스레드 작업: 약 965ms → 745ms

이 수치들은 로컬 통제 환경의 Lighthouse 결과이며 실제 사용자 RUM 데이터가 아니다.

## 표현 시 금지 사항

- 서버 DB 조회까지 사라졌다고 표현하지 않는다.
- 전체 API 요청이 4회에서 0회가 됐다고 쓰지 않는다.
- LCP가 55% 개선됐다고 쓰지 않는다.
- 55.1%는 **대시보드 핵심 데이터 표시 시간** 개선율이다.
- 운영 환경 전체 사용자의 평균이라고 표현하지 않는다.
- 측정하지 않은 매출, 이탈률, 사용자 만족도 개선을 주장하지 않는다.

## 한 줄 핵심 요약

> 서버가 이미 알고 있는 데이터를 빈 HTML 뒤에서 다시 요청하던 구조를, 서버가 정확한 수치를 포함해 처음부터 전달하는 구조로 바꾸고 실제 핵심 데이터 표시 시간을 55.1% 단축한 사례다.
